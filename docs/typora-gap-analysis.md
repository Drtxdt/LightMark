# LightMark vs Typora 剩余差距清单

> 更新时间：2026-06-22

本文档只保留 LightMark 当前仍未完整支持、或还明显弱于 Typora 的能力。已经落地的功能不再作为 gap 追踪，例如：查找替换面板、设置界面、导出 PDF/HTML/PNG/Pandoc 多格式、GitHub 风格警示框、内联/块级 HTML、代码块语言控件、图片粘贴/拖入、Mermaid/公式导出、主题切换与原生窗口适配。

---

## 一、P0：影响日常写作可靠性的缺口

### 1.1 自动保存与崩溃恢复

| ✓ | 任务 | 说明 |
|---|------|------|
| | 自动保存 | 支持定时保存、失焦保存或用户可配置的自动保存策略 |

## 下一步建议

下一步优先级最高的是 **自动保存与崩溃恢复**。

理由：

1. 这是编辑器的底线能力。导出、HTML、警示框、主题这些已经改善了体验，但只要存在未保存内容丢失风险，用户就不敢长期把真实文档交给 LightMark。
2. 它会顺手建立后续文件可靠性的基础设施：保存状态、草稿缓存、文件时间戳、冲突检测、会话恢复都依赖同一套状态模型。
3. 实现路径可控，可以先做窄版：普通文件每 30 秒和失焦保存草稿到本地 JSON/草稿目录，启动时提示恢复；大文件模式先只记录 pending edits 和当前 session，不急着做完整自动写回。

建议第一阶段只做：

| ✓ | 任务 | 说明 |
|---|------|------|
| | 草稿存储 | 按文件路径 hash 存储 `content`、`mtime`、`updatedAt` |
| | 定时草稿 | 文档脏时每 30 秒写入草稿，不直接覆盖原文件 |
| | 启动/打开恢复提示 | 打开文件时发现草稿比磁盘新，提示恢复、丢弃、查看差异 |
| | 保存后清理草稿 | 成功保存当前文件后删除对应草稿 |
| | 状态栏提示 | 显示“草稿已保存/恢复草稿/草稿保存失败” |
