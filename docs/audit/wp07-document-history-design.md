# WP07 文档级连续撤销：实施设计与验收入口

状态：2026-09-08，主负责人设计，尚未实现或验收。依赖 WP05 的真实保真映射与恢复入口、WP06 的局部编辑提交边界。当前 `EditorShell` 在模式切换时重建组件，PM 与 CM 分别维护历史；保留组件名称或序列化当前文档不能解决跨模式撤销。

## 行为契约

- 历史属于原始文档对象，而非当前 pane、标签 id 字符串或编辑组件。另存改名不创建新历史；两个文档不能相互消费历史。
- 可视化编辑后切源码，撤销撤回上一项内容操作；继续切模式、撤销与重做时顺序连续。撤销保持当前选定模式，转换仅更换该模式显示的内容。
- 模式切换、滚动、焦点、公式显示属性与 Markdown 临时标记展示不成为内容历史项。保存不清空历史。
- 粘贴、格式化、公式提交、表格结构命令分别有明确操作边界。组合输入作为一次编辑；组合期不强行结束 IME 来执行文档撤销。
- 新编辑截断当前文档的 redo 分支。外部重载形成明确的文档代次边界，并保留旧编辑的恢复材料；旧坐标不能直接应用到新磁盘版本。

## 状态归属与记录方式

增加文档级协调器，由两个编辑器适配器报告真实内容事务。协调器持有不可变内容表示、前后选区书签、操作来源、文档代次、单调 revision 和历史游标。记录不得包含 EditorView、NodeView、DOM、事件处理闭包或已销毁组件的 dispatcher。

每次输入不能调用全文 Markdown 序列化或 JSON 深拷贝。可视化端持有不可变 PM doc 与对应源码 piece/provenance 根；源码端持有 CM 的不可变 Text 与换行元数据。相邻历史项复用不可变结构，增量记录真实变更范围及 inverse。完整字符串仅在已经需要的保存、模式转换、恢复导出等边界生成。被历史引用的旧 piece 根不因 snapshot checkpoint 被丢弃。

统一历史必须覆盖结构变化、临时语法编辑、局部公式提交和源码任意编辑，不能只消费当前 plain-leaf helper 的成功 patch。缺少合法转换时保留原内容表示、源 bytes 和本地草稿，报告转换失败；不能跳过操作或用规范化全文替代精确保真。此情况也不能被标记为 WP07 验收通过。

记录事件至少区分内容、展示、外部替换与历史重放。根 transaction 和由它产生的内容 append transaction 归属同一操作，展示 append 不增加历史项。原生 PM/CM 历史不能与文档协调器同时响应一个 Ctrl+Z；所有工具栏、菜单、快捷键与程序命令使用同一文档入口。适配器可以借助引擎的 transaction 能力，但不得依赖未公开的 history 内部对象形状。

## 撤销的两阶段提交

1. 固定原始文档、会话、代次、revision、当前历史游标和候选条目。未提交局部输入先按已确认的提交语义处理；组合期延期。处理后重新固定候选，不能继续使用提交前的旧游标。
2. 在候选不可变状态上应用 inverse/forward，验证 expected 片段与来源坐标，再为当前模式准备内容、保真状态和映射后的选区。失败时不动当前文档和游标。
3. 再次校验会话及输入版本，一次发布候选状态并推进游标。该 transaction 标记为历史重放，不再次追加历史。发布后按同一变更更新 dirty、派生信息和保存 revision。

异步转换期间切页，只允许结果归属原始文档；已销毁的 view 不接收焦点或 DOM 更新。转换期间发生新输入时拒绝旧候选，不覆盖输入，不按新位置猜着重试。新挂载视图由文档状态恢复，不能从上一次 pane 的全局投影猜测。

## 分组、内存和恢复格式

先从安装版本核对 PM/CM 的实际分组规则，以连续输入、相邻删除、选择跳转、粘贴、组合输入和明确命令建立对照测试，再提取文档统一分组策略。模式切换结束当前组但不追加历史项。不能把一整次模式会话合成唯一撤销项，或默认每字符一个操作以掩盖集成问题。

本地代码核查：Tiptap PM 实际解析到 3.23.5，历史实现为 `prosemirror-history@1.5.0`。其默认 `newGroupDelay` 为 500ms，并结合映射后变更范围、composition 标记与 appendedTransaction 决定分组；`closeHistory` 显式结束当前组。已安装 CM commands 同样默认 500ms，但普通连续合并限于相邻 `input.type`/`delete` 类操作或没有 userEvent 的变化；`input.type.compose` 可继续前一组，`isolateHistory` 提供 before/after/full 边界。两套规则不完全相同，不能只拷贝一个 500ms 计时器充当历史协调器。上述来自安装代码，不是用户行为验证；生产对照需使用这些真实引擎事务。

历史容量与内存需要测量：记录事件数、保留的唯一 PM/CM/source 根、增量 bytes 和峰值内存。清理 redo 与关闭文档时释放不再引用的结构。当前没有经测量批准的历史内存预算，不能在此编造达标值。

当前 v3 恢复格式对普通 PM/CM 历史只接受 `unavailable + reason`。安装版 CM `HistEvent.toJSON/fromJSON` 丢弃 effects，而源码 EOL 恢复依赖自定义 inverse effects；不能直接套用其 JSON 当作完整历史。后续恢复格式应显式保存协调器的版本、游标、可达内容 checkpoint、增量及选区关系，逐项校验后导入。未知版本或残缺链拒绝自动应用，继续保留原恢复文件。

## Luna 的分片与主负责人验收

1. 用当前真实 PM/CM 建立失败用例：可视化改字 → 源码改字 → 可视化连续撤销到原文再重做。附混合 EOL/BOM、公式提交和格式化对照。先证明现状失败，避免只测协调器 mock。
2. 独立实现协调器、不可变事件和候选提交规则；测试乱序完成、旧游标、跨文档、redo 分支、失败不改状态。主负责人审查后再连接两种编辑器。
3. 串行接 WYS、SourceEditor、文档 store 和命令入口；同一核心不并发修改。移除重复消费历史的路径，保留各能力行为测试。
4. 将历史扩展进专用恢复格式，再做隔离 Windows 原生闭环。逐次比较精确 Markdown、选区、dirty、历史游标与磁盘；覆盖跨标签、分屏、另存后撤销再保存。

验收必须同时证明常规同模式撤销没有退化，以及跨模式目标契约成立。纯模块测试、类型检查与构建通过都不能代替实际编辑器操作。该包独立于性能优化和视觉调整；回退时回退整个历史接入单元，保留失败用例，并继续阻止不满足历史契约的版本发布。
